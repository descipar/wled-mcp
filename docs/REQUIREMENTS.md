# Requirements specification

Version: 0.4, 2026-11-06. State: v1 design baseline refined by issue #2, with confirmed dual-transport scope. All stage-1 work packages under tracker [#1](https://github.com/descipar/wled-mcp/issues/1) are closed, and the tracker itself was closed as completed on 2026-11-06. Hardware evidence covers one controller on one firmware (see [VALIDATION.md](VALIDATION.md) and [TRACEABILITY.md](TRACEABILITY.md)); the items listed there as pending stay pending.

This document defines **stage 1**. Future public-release and product requirements use `S2-` IDs in [STAGE-2.md](STAGE-2.md) and separate tracker [#15](https://github.com/descipar/wled-mcp/issues/15). Stage-2 direction does not change repository visibility or silently add release-publication requirements to stage 1.

## 1. Authority and meaning of priorities

**Confirmed:** prepare a detailed GitHub project (originally requested as private; amended by [DEC-009](DECISIONS.md#dec-009--public-ready-repository-baseline) to keep its content public-ready without a visibility change) for a standalone WLED MCP server so a later agent can check it out and implement it. Documentation and actionable GitHub issues are required. MCPHub is the initial integration target. That original assignment covered planning, without implementation, installation or hardware mutation. The subsequent issue-2 instruction authorizes the scoped contract work and review workflow recorded in [issue decisions](decisions/issue-2.md); it does not commission all downstream issues.

**Confirmed scope update:** v1 supports both Streamable HTTP for independent service operation and stdio for client-managed launch via uvx. Both expose identical WLED tools and domain behavior. The original stdio-only transport proposal is superseded. Updating this scope/backlog does not commission runtime implementation or deployment.

**Proposed baseline:** the feature scope and technical defaults below synthesize the preceding discussion. They are design proposals, not individually approved product requirements. A later implementation request can accept or adjust this baseline. Unknown device facts must not be invented. Issue #2 resolves technical defaults in [TOOL-CONTRACT.md](TOOL-CONTRACT.md) under agent design authority; this does not label each choice human-confirmed.

Priorities: **Must** = required for the proposed first usable release; **Should** = useful v1 enhancement, may be deferred with an explicit decision; **Later** = outside first release. Requirement IDs remain stable when priorities or wording evolve. A Must blocked by unavailable hardware can be implemented and mock-tested, but the release remains hardware-unverified.

## 2. Context and intended users

Target deployments include self-hosted MCPHub instances on small Linux hosts using Docker Compose. Persistent `/app/data` and `/app/binaries` paths in examples are proposed container locations, not details of a particular user's installation. Inspect the actual runtime, architecture and mounts during deployment.

Several agent clients can use the hub. This server connects directly to WLED controllers and exposes their capabilities through a consistent MCP interface: device inspection, lighting controls, segment layout editing and preset management. It operates independently of other home-automation systems. Feature scope is determined by WLED capabilities and this project's requirements.

Primary user: a person operating one or more WLED controllers who asks an agent for lighting changes. Secondary user: the implementing/maintaining agent, who needs stable contracts, helpful errors, reproducible installation, and a narrow operational footprint.

## 3. User scenarios

| Scenario | Expected behavior | Requirements |
| --- | --- | --- |
| “Which WLED controllers are configured and reachable?” | List configured names immediately; reachability is explicit and bounded | DEV-01, DEV-02 |
| “Show the desk strip's effects and current layout.” | Read device-specific names, IDs, active segments and capabilities | READ-01, READ-02 |
| “Make the first section warm white and the remainder blue.” | Agent reads LED count/capabilities, proposes or applies an explicit layout; unrelated controllers stay untouched | SEG-01–04, CTRL-01 |
| “Change only segment 2's effect speed.” | Patch only that segment and speed; preserve other fields and segments | SEG-01, SEG-03 |
| “Save this as Evening.” | Allocate an unused persistent preset ID; report name/ID and verify persistence | PRE-01–03 |
| “Replace preset 5 with this layout.” | Explicit overwrite of that ID with restorable prior preset data; no accidental second save on timeout | PRE-02–04, REL-02 |
| “Turn both configured strips off.” | Execute per device with individual outcomes; no claim of an atomic transaction | MULTI-01 |
| Controller disconnects during a request | Return a bounded, informative failure or uncertain write outcome | REL-01–03 |

## 4. Functional requirements

### Device selection and reads

- **DEV-01 Must — Named inventory.** Load a TOML file containing unique stable device IDs, human names and explicit base URLs. Every device-targeted tool requires `device_id`; no implicit default-device writes. Reject duplicate IDs, invalid entries, URL credentials, query strings/fragments and unsupported URL schemes at startup. Only HTTP(S) controller roots are allowed. DNS host labels may contain interior `_`; a host whose last label is numeric must be a canonical dotted-quad IPv4 address (non-canonical numeric hosts such as `1.2.3` or `999.1.1.1` are rejected); a startup error names a rejected entry by its list position and field without echoing values.
- **DEV-02 Must — Explicit availability.** List configured devices without network access by default. Optional bounded reachability probes return independent per-device outcomes. One offline device must not prevent listing or accessing others.
- **DEV-03 Should — Explicit reload.** Reload a changed inventory through a documented restart or controlled reload procedure. Invalid replacement configuration must not silently replace a working inventory. No automatic network discovery in v1. Status (#13, ISSUE-13-DEC-001): stage 1 provides the documented restart procedure with rollback in [DEPLOYMENT.md](DEPLOYMENT.md#changing-the-inventory); an invalid file stops startup with exit 2 before any change. [#16](https://github.com/descipar/wled-mcp/issues/16) adds `wled-mcp config validate` (same validator and messages as startup, no device contact) as the step before the restart; in-process reload is not built (ISSUE-16-DEC-001).
- **READ-01 Must — State and information.** Read state plus device identity, firmware version, LED count, segment limit and reported color capabilities. Keep raw observed API fields available where useful, with unverified/absent capability fields reported as unknown rather than false.
- **READ-02 Must — Device-specific catalogs.** Read effect names/IDs and palette names/IDs from the target controller. Preserve original IDs; do not reindex filtered entries or hardcode a universal effect count. Combine metadata when available and handle unsupported metadata endpoints without losing the basic catalog.
- **READ-03 Should — Bounded metadata cache.** Cache catalogs for a proposed 300 seconds, support explicit refresh, invalidate on observed firmware change, and label cached/stale data. Never silently substitute cached state for a requested current state read.

### Lighting and segment behavior

- **CTRL-01 Must — Typed state controls.** Support master power, brightness 0–255, transition duration in clearly documented milliseconds, RGB/RGBW colors when supported, effect and palette selection, speed and intensity. Zero, false, empty and omitted values must remain distinguishable. Resolve effect/palette names only when unambiguous; otherwise return candidates and require an ID or precise name. Apply the contract's remembered/effective brightness distinction and explicit zero/off rules, separately for master and segment firmware behavior. Transition is one-call `tt`: integer 0–65500 ms, nearest 100 ms half upward; reject 1–49 ms, transition-only requests and unrepresentable deadline/target combinations.
- **SEG-01 Must — Patch semantics.** Update explicit existing segment IDs without altering unrelated fields/segments. Omitted fields retain their values; proven targeted compensation may resend an omitted field to counter a firmware side effect (for example clearing a name on geometry change). Reject an unrepresentable preservation plan before writing; do not round-trip the whole configuration. No automatic deletion or “cleanup” of segments in patch mode.
- **SEG-02 Must — Replace semantics.** A separate tool replaces the active segment layout with explicit IDs and ranges, identifies old segment IDs that must be removed, and deletes only those IDs. Never append a fixed number of dummy segments. Read the current layout first, calculate a plan, then verify the result. Existing desired active IDs preserve omitted fields; new/reused inactive IDs require colors and explicit resolved defaults from the contract. Profile-check allocation/removal behavior, reject silent renumbering and sparse creation that cannot preserve IDs, and expose partial multi-step outcomes. Document that cross-client changes can race with the plan.
- **SEG-03 Must — Validation.** Validate all segments before writing: unique/nonnegative IDs, `start < stop`, exclusive stop within LED count, segment-count/ID limits when known, valid colors and channel counts, brightness/speed/intensity bounds, effect/palette existence, positive grouping, nonnegative spacing, documented offset handling. Reject ambiguous overlapping ranges in replacement mode by default; if overlap support is later needed, make it explicit. Unknown capabilities must not be silently guessed. RGB-only requests require three color channels, RGBW four; retain omitted existing color slots. New/moved ranges require validated range capability evidence. Scalar patches may preserve existing overlap; range changes reject introduced overlap against untouched active segments too.
- **SEG-04 Must — Plan and verify.** Mutating state/layout tools support `dry_run`. A dry run performs bounded reads/validation but no controller, snapshot, temporary-file or retention writes, and shows resolved defaults, compensation, exact affected IDs and required backup. It reserves no slots. After an actual write, read back relevant state and compare normalized values; animation progression and normal unrelated transient fields are not equality requirements. Report applied, not applied, mismatch, or unknown rather than treating HTTP 200 alone as proof.
- **SEG-05 Should — Segment options.** Support segment power, brightness, up to three colors, grouping, spacing, offset, reverse, mirror, selection and name where supported. Add RGBW and CCT through capability-aware fields. RGBW is part of core color handling; CCT and 2D matrix geometry need real device requirements before becoming Must. Status (#13, ISSUE-13-DEC-001): power, brightness, up to three RGB/RGBW colors, grouping, spacing, offset, reverse, mirror, selection and name are delivered in `wled_patch_segments` and `wled_replace_layout` (#6/#7); CCT, 2D fields and the remaining segment fields are deferred to [#19](https://github.com/descipar/wled-mcp/issues/19).
- **SEG-06 Later — Matrix and streaming.** Pixel art, image uploads, text scrolling, audio capture, custom realtime animation streaming and DDP are separate scope. Built-in WLED effects remain usable in v1. Status (#13, ISSUE-13-DEC-001): excluded; no owning issue.

### Presets and playlists

- **PRE-01 Must — Inspect and activate.** List persistent presets, read an individual preset's contents and activate a specified existing ID. Use reviewed persistent IDs 1–250, excluding reserved 0 and temporary 255. Recognized empty entries are absent; nonempty unknown/malformed entries remain occupied. Preserve object type/unknown fields; activate only verified safe state/playlist shapes. Do not alter saved contents when activating. Status (#9): implemented and mock-tested (`wled_list_presets`, `wled_get_preset`, `wled_activate_preset`); entry types are `state`, `playlist`, `api-command`, `unknown`. Status (#66): WLED 16 state presets carrying the top-level blending-style key `bs` are classified `state` and activatable (ISSUE-66-DEC-001), mock-tested; the hardware re-check of save then activate on WLED 16 is recorded for one controller in both modes in [VALIDATION.md](VALIDATION.md#issue-12-hardware-acceptance-run-2-2026-11-06) (#12). Controllers and firmware other than WLED 16.0.1 remain unverified.
- **PRE-02 Must — Save current state.** Create a named preset from current state, allocating the lowest free supported persistent ID. Save all segments with brightness and bounds, without deliberate live-output activation. Reject blank/control-containing or over-32-byte UTF-8 names in the reviewed profile. Capture is asynchronous and must be compared to the recorded pre-dispatch state reference. Updating an occupied ID requires explicit `overwrite=true`. Do not allocate a free ID and later overwrite a newly occupied one without noticing the conflict. External clients prevent a true atomic guarantee; document the remaining race. Status (#66): on WLED 16 the save compares `bs` when the live state carries it, and a saved entry that does not classify as `state` is reported by a warning naming only the unexpected keys (ISSUE-66-DEC-001), mock-tested; the hardware re-check of save then activate on WLED 16 is recorded for one controller in both modes in [VALIDATION.md](VALIDATION.md#issue-12-hardware-acceptance-run-2-2026-11-06) (#12). Controllers and firmware other than WLED 16.0.1 remain unverified.
- **PRE-03 Should — Save supplied state.** Save a named, validated supplied layout/state without changing live output where the target firmware supports it. Not part of #9 (ISSUE-9-DEC-001) and not satisfied by it; the default tool has no supplied `state`; do not emulate by implicit apply/save/restore. Status (#18): `wled_store_preset` saves a validated supplied state through one single-entry write that applies it live first (ISSUE-18-DEC-001); the storage-only variant is unsupported on WLED 16 and documented in [contract/presets.md](contract/presets.md); mock-tested, hardware pending.
- **PRE-04 Must — Delete and backup.** Delete one explicitly identified existing preset. Before overwrite/delete, store a validated snapshot of its prior contents atomically in the configured project data directory; if backup fails, abort the destructive write. Backups record device ID, preset ID, firmware, timestamp and format version. Prevent path traversal; keep per-device retention configurable. Use the version-1 envelope and bounded explicit restoration workflow in the contract. Restoration execution remains Should and deferred pending a safe single-entry storage adapter; export/inspection alone is not restore evidence. Never use automatic blind rollback, stored-command execution or bulk upload as a shortcut. Status (#8): the snapshot store, retention and a read-only restore plan helper exist and are mock-tested; restoration execution stays deferred and the manual procedure is in the TOOL-CONTRACT. A restore tool is deferred to [#18](https://github.com/descipar/wled-mcp/issues/18) (ISSUE-13-DEC-001). Status (#9): `wled_save_preset` (overwrite) and `wled_delete_preset` take the snapshot before dispatch, mock-tested; hardware check H06 (snapshots before overwrite and delete) is recorded for one controller on WLED 16.0.1 in [VALIDATION.md](VALIDATION.md#issue-12-hardware-acceptance-2026-11-06) (HTTP mode) and [VALIDATION.md](VALIDATION.md#issue-12-hardware-acceptance-run-2-2026-11-06) (stdio mode) (#12). Status (#18): `wled_restore_preset` restores one `state` or `playlist` snapshot entry with exact device and firmware match, its own prior snapshot and readback verification, and `wled_list_snapshots` lists the snapshots; mock-tested in [validation/issue-18.md](validation/issue-18.md), hardware pending.
- **PRE-05 Must — Persistent outcome.** After save/delete, read persistent preset data until the expected condition is observed or a bounded deadline expires. Compare name and included captured state fields in persistent data, not merely a new ID/name or live state. Distinguish flash persistence delay, failure and uncertain outcome. Never automatically replay an uncertain save, delete or allocation. Status (#9): bounded polling of `/presets.json` is implemented and mock-tested.
- **PLAY-01 Should — Playlists.** Inspect and activate existing playlist presets. Creating/editing playlists, duration/repeat rules and interaction with active playback are a later enhancement unless requested; do not interpret playlist objects as ordinary color presets when editing. Status (#9): existing playlists are listed, read and activated (members must be plain state presets); replacing a playlist is rejected; no tool creates or edits playlists. Playlist authoring is deferred to [#18](https://github.com/descipar/wled-mcp/issues/18) (ISSUE-13-DEC-001). Status (#18): `wled_restore_preset` restores playlist snapshots and `wled_save_playlist` creates or replaces a playlist of existing state presets with validated durations, transitions, repeat, end and shuffle; saving starts it (ISSUE-18-DEC-001) and is refused while a playlist runs; `wled_import_presets` imports one playlist per call with its members. Mock-tested in [validation/issue-18.md](validation/issue-18.md), hardware pending.

### Multi-device behavior and advanced operations

- **MULTI-01 Must — Independent outcomes.** Different devices can be used by separate tool calls without global serialization. Multi-device orchestration belongs initially to the agent: results are per controller, and no synchronized or all-or-nothing behavior is promised. Within one server process serialize a device's write/verify sequence; document limits across multiple server processes and other WLED API clients.
- **ADV-01 Should — Restricted raw state patch.** Provide an advanced state patch only if typed tools leave a demonstrated gap. Accept a JSON object, not a JSON-encoded string. Restrict target to the configured controller's state API, reject unknown fields by default and recursive excessive payloads, and block hardware/network/security/firmware settings. A raw patch cannot bypass preset overwrite, backup, delete or layout replacement rules. Default disabled. A documented allowlist is required before enabling it. Status (#13, ISSUE-13-DEC-001): excluded from stage 1; `raw_state_patch = true` stays rejected at startup and no tool is registered; no owning issue.
- **ADV-02 Later — Configuration management.** Timer editing, firmware updates, Wi-Fi changes, reboot, hardware pin/bus configuration, factory reset, filesystem uploads and arbitrary URL forwarding are outside v1. Status (#13, ISSUE-13-DEC-001): excluded, including timer editing; no new issue.

## 5. Nonfunctional and protocol requirements

- **MCP-01 Must — Standard transports.** Expose both stdio and Streamable HTTP using the official Python SDK or a justified maintained alternative. Select with `--transport stdio|streamable-http`; default stdio starts no listener. HTTP is an independent service with `/mcp`, configurable bind/port and lifecycle. Both modes support initialization, tools/list and tools/call through SDK negotiation, with identical tools, schemas and domain behavior. HTTP must not be implemented as only legacy SSE or ordinary REST. Tools have accurate annotations; annotations are not authorization enforcement.
- **MCP-02 Must — Machine-readable results.** Return structured, stable result/error objects plus a compact text fallback. Tool execution failures set MCP `isError` appropriately; do not bury failures in an apparently successful string. Protocol errors and expected device/tool errors remain distinct. Preserve valid structured results for partial or uncertain outcomes. Use the contract's application/verification table, equivalent JSON text fallback, and `isError = !ok`; ACK alone is not verified application.
- **MCP-03 Must — HTTP endpoint access.** Default HTTP binding is 127.0.0.1:8000; private container-network binding is explicit. Exact Host authorities and supplied Origin allowlists reject as 403 before device actions; absent Origin is allowed for authenticated non-browser clients. Every HTTP method requires runtime bearer protection (401 for invalid/missing credential) or a documented equivalent proxy with no direct bypass. Missing/conflicting auth configuration fails before listening. Hub authentication does not protect the independently reachable endpoint. Keep credentials outside CLI values, committed examples and logs. Document the private shared-credential deployment's limits; a full OAuth service is outside v1.
- **MCP-04 Must — Multi-client HTTP lifecycle.** Multiple HTTP sessions share inventory, WLED client, metadata caches, snapshots and per-device write/verify locks in one process. Use SDK stateless JSON responses with no session IDs, replay store or server stream; initialization/negotiation still apply. Shutdown stops admission, drains within existing operation deadlines, closes shared resources and never requeues unfinished writes. Disconnect/reconnect must not imply write cancellation or trigger mutation replay. Use one worker for v1 unless cross-process coordination is implemented; ordinary process-local locks do not coordinate separate workers.
- **REL-01 Must — Bounded I/O.** Design defaults: 3-second connection timeout, 10-second overall device-operation deadline and at most one retry per safe read within that deadline; persistent polling starts at 100 ms. Limits are configurable, with maximum response/payload sizes selected and tested during client implementation. A tool deadline must include verification and retries rather than multiplying unbounded per-stage timeouts.
- **REL-02 Must — Uncertain writes.** After a response timeout/reset, report that a write may have applied. Attempt bounded readback when possible, but never label a mismatch as proof the command was not previously applied. No automatic write replay, including preset allocation. Distinguish successful, failed, and indeterminate application/persistence.
- **REL-03 Must — Coexistence.** Preserve unknown fields in backups and untouched state. Never read-modify-write the whole config to change a single light value. Document that the WLED UI, other API clients, playlists, timers, realtime senders and other agents may change state concurrently. Verification can report interference; do not continually fight another controller.
- **OPS-01 Must — Lightweight runtime.** Support a Python Streamable HTTP service independently of MCPHub and a stdio process launched by the client via uvx. One shared implementation supplies both transports. HTTP may use a dedicated Docker Compose service or equivalent managed process; stdio does not require that service. No database, browser UI, cloud service or mDNS dependency. Measure startup/idle memory for each mode exercised on the target; no unmeasured resource claim is an acceptance result.
- **OPS-02 Must — Reproducible delivery.** Version the package, pin/lock resolved dependencies, document console start, persist application/data paths across hub recreation, and provide update/rollback instructions. Runtime bootstrap must not depend on a developer's editable checkout or unpinned `latest` resolution.
- **OPS-03 Must — Logs and privacy.** In stdio mode stdout carries MCP only; diagnostics go to stderr in both modes. Avoid logging credentials, full configuration dumps or unsanitized HTTP bodies. Real devices, secret-bearing backups and runtime files are excluded from Git. Only explicitly selected HTTP mode opens the configured listener.
- **OPS-04 Should — Diagnostics.** Include application version and capability diagnostics in read results, with actionable messages for bad configuration, unsupported firmware, unavailable backup storage, offline devices and invalid responses. Status (#1, ISSUE-1-DEC-001): the following diagnostics count as delivered for stage 1: the application version (`wled-mcp --version` and `diagnostics.server_version` in `wled_get_state`), unknown-capability reporting (`diagnostics.unknown_capabilities` in `wled_get_state`, with unreported capabilities as `null`), categorized error codes in the result envelope (for example `CONFIG_ERROR`, `UNREACHABLE`, `TIMEOUT`, `INVALID_RESPONSE`, `UNSUPPORTED_CAPABILITY`, `BACKUP_FAILED`, `WRITE_OUTCOME_UNKNOWN`) with a reconciliation hint, and safe startup configuration diagnostics on stderr (exit code 2, values not echoed). [#16](https://github.com/descipar/wled-mcp/issues/16) adds the read-only `wled-mcp doctor` with a fixed category, code and action for every listed condition, and a startup advisory on stderr when the backups location is not writable ([CLI contract](contract/cli.md#ops-04-conditions)).
- **OPS-05 Must — Both deployment modes.** Supply reproducible HTTP-service/Docker and uvx/stdio instructions plus MCPHub examples, persistent inventory/backups, explicit version pinning, secret injection and update/rollback procedures. The service runs independently of the hub and can be restarted/updated separately. Document host/container address differences, single-worker operation, bounded shutdown and a liveness check that does not change devices. Actual deployment evidence must identify which mode was exercised.
- **TEST-01 Must — Meaningful verification.** Automated tests cover the contract's hard cases and run without devices or LAN access. An opt-in hardware checklist records firmware, capabilities, observations and restoration. Unrun hardware tests remain visibly pending.

## 6. Explicit non-goals

No independent automation scheduler, cloud remote access, OAuth server, graphics editor, public package publishing, or guarantee of simultaneous multi-controller frames. No blanket “supports all WLED versions/features” claim. No automatic reconfiguration of an MCPHub-style host or device firmware as a prerequisite.

## 8. Completion definition

The first usable release implements every Must, documents any deferred Should, passes the automated acceptance suite, is installable reproducibly, and has read-only integration evidence through the actual hub. Physical write acceptance additionally requires explicitly authorized checks on selected devices. Until those run, label the build “implemented, hardware write validation pending”; do not silently downgrade Must requirements to claim completion.

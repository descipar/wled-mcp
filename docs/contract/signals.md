# Temporary signals (`wled_start_signal`, `wled_get_signal_status`, `wled_cancel_signal`, #28)

Requirements S3-SIGNAL-01 and S3-SIGNAL-02 ([STAGE-3.md](../STAGE-3.md)). Decisions:
[ISSUE-28-DEC-002](../decisions/issue-28.md) (design defaults, a technical proposal accepted by
the coordinator, not a human decision) and [ISSUE-28-DEC-001](../decisions/issue-28.md) (the
hardware authorization for the evidence). Evidence: [validation/issue-28.md](../validation/issue-28.md).
Examples use synthetic IDs.

A **signal** shows one RGB colour on explicitly listed existing segments of **one** configured
device for a bounded time and then puts back **only the fields it changed**, and only if they
still hold what the signal set. If someone changed them in the meantime, the server reports
`skipped_conflict` and writes nothing. Both transports use these same operations.

It is **not a scheduler**: no recurrence, no deferred start, no queue, no replace policy, no
persistence, no preset created, overwritten or activated, and no replay of a write whose outcome
is unknown.

## Tools

| Tool | Class | Hints (read-only / destructive / idempotent / open-world) | Reachable in |
| --- | --- | --- | --- |
| `wled_start_signal` | `control` | false / false / false / false | `control`, `full` |
| `wled_cancel_signal` | `control` | false / false / true / false | `control`, `full` |
| `wled_get_signal_status` | `read` | true / false / true / false | every profile |

Why `control`: live device output only; no snapshot, file or device storage is touched and
nothing is persisted, so no tool is `manage` ([profiles](profiles.md)). A device whose ceiling is
below `control` refuses `wled_start_signal` with `ACCESS_DENIED`, also for `dry_run`.
`wled_cancel_signal` has no `device_id`: the signal's device already passed its ceiling at start,
and a ceiling cannot change without a restart. Profiles are not tenancy: any caller that can
reach the tool can cancel any signal.

### Requests

| Tool | Fields |
| --- | --- |
| `wled_start_signal` | `device_id` (1-64 characters), `segment_ids` (1-16 unique integers >= 0, existing active segments), `color` (exactly three integers 0-255, RGB), `duration_seconds` (integer 1-300, required, no default), `dry_run` (default `false`) |
| `wled_get_signal_status` | optional `operation_id`; without it: all active signals and the most recent 32 ended ones, active first, each newest first |
| `wled_cancel_signal` | `operation_id` |

All requests reject unknown fields and wrong types. The operation ID is generated by the server,
`sig-` plus 16 lowercase hex characters, and is never taken from a client. Example:
`sig-0123456789abcdef`.

The signal always uses the **Solid** effect (resolved by name from the device's own effect
catalog) and the device's own brightness. A target segment that reports four channels gets white
0 appended; a white-only segment or one without capability evidence is refused
(`UNSUPPORTED_CAPABILITY`). There are no brightness, effect or palette options.

## Owned fields

The signal writes, and so owns, exactly these fields. It captures them before the write,
compares them before restoring and restores only them.

| Scope | Field (wire key) | Written when | Compared before restore | Restored to |
| --- | --- | --- | --- | --- |
| master | `on` | the master was off | still `true` | `false` |
| segment | `col[0]` | always (slot 0, full channel width) | still the written colour | the captured slot 0 |
| segment | `fx` | always | still the Solid effect ID | the captured effect ID |
| segment | `on` | the segment was off | still `true` | `false` |

The comparison has the same semantics as the functions that verified the apply
(`matches_segments`, `matches_set_state`; a test pins the agreement) plus three side-effect checks (a playlist, realtime data or a nightlight
that started meanwhile) and the geometry of the targets (a removed or resized target segment is a
conflict). **Not compared and never written:** master brightness, the transition, segment
brightness, speed, intensity, palette, custom sliders, checkboxes and colour temperature, colour
slots 1 and 2, names and selection, untargeted segments, the running preset marker and every
counter or animation progress. An external change there is preserved. The effect's animation phase
cannot be captured and restarts with the effect change.

The apply is one combined state write (`on` only when the master was off, plus the segment
objects) built by the existing segment and master planners and read back before the timer starts.

## Unsupported device states

These are refused at start, before any write, as `VALIDATION_ERROR` with `application` =
`not_attempted` and the stable `data.reason` (no new error code):

| `data.reason` | Condition (fresh read under the device lock) |
| --- | --- |
| `segment_unknown` | a target ID is not an existing active segment |
| `capture_incomplete` | a target segment does not report `on`, colour slot 0 and the effect (`UNSUPPORTED_CAPABILITY`) |
| `color_capability` | a white-only segment or one without capability evidence (`UNSUPPORTED_CAPABILITY`) |
| `playlist_active` | a playlist is running |
| `realtime_active` | the device receives realtime data |
| `nightlight_active` | a nightlight is running |
| `segment_frozen` | a target is frozen, or the master is off and any segment is frozen (turning the master on unfreezes every segment) |
| `master_off_other_segments` | the master is off and another active segment would light up when it turns on |
| `brightness_zero` | the master's remembered brightness is 0, or a target is off with brightness 0 |
| `effect_unavailable` | the device has no unambiguous `Solid` effect (`UNSUPPORTED_CAPABILITY`) |

A running preset marker is allowed: any state write clears it and the restore does not re-activate
the preset (a warning says so). Rejecting is chosen over guessing an inverse for a playlist,
realtime or a nightlight.

## Overlap and limits

At most **one signal per device** (while starting, active or restoring) and at most **eight per
process**. A second start on the same device is refused with `reason` `signal_active` and
`data.active_operation_id`; the ninth is refused with `signal_limit`; during shutdown a start is
refused with `shutting_down`. Signals are never queued or replaced. The slot is reserved before
the first read and freed when the start fails before dispatch, when the apply is uncertain, and
when the signal ends. Different devices run independently. Other tools may still write to the
device during a signal; the conflict check exists for exactly that.

## Results

### `wled_start_signal`

Success is `ok=true`, `applied` / `verified`, with `data.operation_id`, `status` (`active`),
`segment_ids`, `started_at`, `expires_at`, `duration_seconds`, `owned` (each field with its
`captured` and `applied` value), `restoration_plan`, `unowned_observed` (display only), `timing`
and `plan` (the exact payload). A start failure before dispatch (unreachable, timeout, any
refusal) creates no record and no ID.

If the apply was sent but could not be verified (`WRITE_OUTCOME_UNKNOWN`, `VERIFICATION_MISMATCH`),
no timer starts and **nothing is restored automatically**: the envelope is the engine's uncertain
envelope with `data.operation_id`, `data.reason` `apply_unverified` and `data.captured`, and a
terminal `uncertain` record is kept for the status tool. Read the state and decide, using the
captured values.

`dry_run` reads the device (bounded reads under the lock) and returns the same plan, owned fields
and restoration plan, or the same refusal; it creates no record and reserves nothing.

### Status and restoration

| `status` | Meaning |
| --- | --- |
| `active` | applied, timer running |
| `restoring` | ended by `ended_by` = `expired`, `cancelled` or `shutdown`; the restore is in progress |
| `restored` | the owned fields matched and one verified restore write was made |
| `skipped_conflict` | a compared field, the geometry or a side-effect check differs; nothing was written; the device keeps the external state |
| `uncertain` | the restoration could not be established |

`data.restoration` carries `result`, `application`, `verification`, `error_code`, `differences`
(at most 20 entries `{scope, id, field, expected, observed}`), `write_attempted` (did a POST
leave) and `attempts`. An `uncertain` restoration keeps the `captured` values in `owned` so that
the state can be restored explicitly. The wall-clock timestamps are `started_at`, `expires_at`
and `ended_at`.

`wled_get_signal_status` reads process memory only and contacts no device. An unknown ID is
`VALIDATION_ERROR` with `reason` `unknown_signal`, which is also what every ID is after a restart.

### `wled_cancel_signal`

Cancel means "end the signal now and put the device back if it is still ours": it runs the same
conditional restore as expiry and waits for the result. There is no cancel-without-restore (patch
the segment to keep a colour). `restored` is `ok=true` `applied` / `verified`; `skipped_conflict`
is `ok=true` `not_attempted` with a warning (the cancel succeeded and the device was left as
found); `uncertain` is `ok=false` with the engine's error. Cancelling an already ended signal is
`ok=true`, `not_attempted`, with the terminal record and a warning; cancelling one that is already
restoring waits for that result and never starts a second restore.

## Retry policy: re-read and decide, never replay

Only an **expiry-driven** restore that failed **before any POST left** (device unreachable, or
the operation deadline expired while reading or waiting for the lock) is tried once more after
5 seconds, as a fresh attempt: fresh read, fresh comparison, then the write. A restore whose POST
left (readback unreadable, mismatch, transport error) is never retried. A cancel or shutdown
restore makes one attempt only. A device that comes back later receives no further write.

## Locks and access context

- Capture and apply happen inside one `write_verified` call: one lock hold for the fresh read, the
  checks, the capture, the planning, the POST and the readback.
- While waiting, the lock is **not** held.
- The restore is again one `write_verified` call: it re-acquires the lock within the operation
  deadline, re-reads state and info, compares and writes, all in one lock hold.
- Each signal is run by **one manager task** (reserve, apply, register, wait, restore). A start or
  cancel only hands work to it and awaits the result, so a cancelled or dropped request never
  orphans an applied signal and never writes by itself. Cancel, expiry and shutdown race through
  one synchronous check-and-set: exactly one restore per signal.
- The signal task sets the access class `control` itself for its whole life, whatever woke it
  (timer, cancel or shutdown), instead of inheriting it from the request. The delayed restore is
  therefore evaluated as a `control` operation against the device's effective ceiling, which
  already allowed `control` at start; it is never `manage` and never the ambient "class unknown,
  assume the highest" case that a restricted deployment refuses ([profiles](profiles.md)).

## Shutdown and restart

**No persistence.** Signals live in process memory. Nothing is written to the data directory, no
metadata or journal exists, and nothing is recovered or replayed after a restart.

- **Orderly shutdown** (stdio end of input or interrupt, HTTP SIGTERM or SIGINT after the listener
  drained): new starts are refused, and every active signal makes **one** conditional restore
  attempt (same comparison, no retry), concurrently, within a total budget of 5 seconds. Whatever
  has not finished is abandoned and may be left applied (logged as `shutdown_incomplete`; an
  abandoned POST is uncertain; a start whose apply is still in flight at shutdown is awaited up to
  the operation timeout, so the exit can take longer than the budget in that rare case). The budget stays well inside the documented HTTP grace period
  ([DEPLOYMENT.md](../DEPLOYMENT.md)).
- **Crash, kill, second interrupt, power loss:** a signal still active stays applied on the device
  until someone changes it, and after the next start its operation ID is unknown
  (`unknown_signal`). This is the documented gap. Manual recovery: read the state with
  `wled_get_state`, compare it with the `captured` values the start returned, and restore the
  segment colour, the effect and, if the signal had turned it on, the power, explicitly
  ([segments](segments.md)).
- **Lost connection:** a dropped HTTP or stdio client causes no write at all (no cancel, no
  restore). The timer runs on and the restore happens at expiry. A reconnecting client reads the
  status with the operation ID. A disconnect during the start itself is covered: the task finishes
  and registers.

The statement that a forced interruption leaves possibly applied writes uncertain and never
resumed on restart stays true ([TOOL-CONTRACT.md](../TOOL-CONTRACT.md#transport-access-and-lifecycle)).

A later option, a small journal with an `interrupted` status on the next start (never replayed),
is possible but not part of this contract; it would make `wled_start_signal` a `manage` tool.

## Timing is best effort

The duration is measured on the process monotonic clock from the verified apply. The restore starts
at expiry plus the lock wait and the device round trips, so the signal can last longer (a slow
device or network, lock contention, a suspended host). The exact physical duration is not
guaranteed, in particular not across an outage; if the device is unreachable the signal may never
be restored (`uncertain`). The firmware's own transition time applies to both changes.

## The remaining external-client race

The comparison and the restore write are one lock hold of this server, but another client that
writes to the device directly (not through this server) between the comparison read and the restore
POST is not detected. WLED offers no compare-and-set. The window is one device round trip.

## Diagnostics and privacy

One bounded INFO line per event (`started`, `restored`, `skipped_conflict`, `uncertain`,
`shutdown_incomplete`) goes to stderr with the operation ID, the status and the error code, and the
configured device ID; never a colour, an address or a state body ([diagnostics](diagnostics.md)).
A delayed restore is recorded as `wled_signal_restore` in the process-local last-control evidence,
so `wled_explain_lighting` ([explain](explain.md)) can attribute a change to this server's own
delayed write.

## Compatibility

Additive: three new tools, no new error code or enum value, no change to an existing schema, no
persistent format ([versioning](versioning.md)). A zone as a target is a possible follow-up
([zones](zones.md)); the explicit segment IDs are the target in this version.

# Runtime diagnostics (issue #20)

Contract for [issue #20](https://github.com/descipar/wled-mcp/issues/20) (S2-ACCESS-03,
OPS-03, OPS-05; scenarios T20-14 to T20-17), second pull request: the correlation ID,
bounded call logs and the `wled_get_service_status` tool. Enforcement of profiles and device
ceilings is in [profiles.md](profiles.md). Decisions:
[ISSUE-20-DEC-001](../decisions/issue-20.md#issue-20-dec-001--default-profile-device-restrictions-status-surface-classes)
(human: no unauthenticated health route, readiness as a read-class tool, a correlation ID as
a result-envelope field) and
[ISSUE-20-DEC-002](../decisions/issue-20.md#issue-20-dec-002--technical-defaults-td-20-1-to-td-20-15)
(coordinator, TD-20-9 to TD-20-12). Evidence: [validation/issue-20.md](../validation/issue-20.md)
(mock and loopback only; no hardware claim).

Everything here is local and passive: there is no outbound telemetry, no polling of
controllers, no file logging and no new network surface.

## Correlation ID

Every tool result the server returns carries `correlation_id` in its envelope: 16 lowercase
hexadecimal characters from the operating system's secure random source, generated by the
server for each `tools/call`. It is the same value in the result text and in
`structuredContent`, and in the one log line of that call. It is never taken from client
input: an argument named `correlation_id` is an unknown field and a `VALIDATION_ERROR`
like any other.

- It is set on every envelope the dispatcher returns: successes, domain errors, validation
  errors and `ACCESS_DENIED`.
- A call that fails with an internal error (`-32603`) has no envelope; its fixed message ends
  with the ID: `Internal operation failure (correlation_id=<id>)`. Nothing else about the
  failure is returned or logged.
- A call to an unknown or disabled tool is the protocol error `-32602` `Unknown tool`,
  unchanged and byte-identical for both, so it carries no ID (it must not reveal which
  names exist). It is still logged, as `unknown_tool`, with an ID in the log line only.
- The field is additive and optional. The output schema declares it as an optional string
  (it is not in `required`); an envelope that was not served (a direct `execute` result, the
  retained examples) omits the key, so those documents are unchanged. Consumers that compare
  two served envelopes must ignore this field because it differs on every call.
- The ID correlates one result with one log line. It is not an identity, a session or a
  secret, and it is not unique across restarts.

## Logging

The server writes one line per tool call to **stderr** (stdout is reserved for stdio MCP and
the line never goes there). The line is built from an allowlist; a field is omitted when it
does not apply.

| Field | Content |
| --- | --- |
| `event` | `tool_call` |
| `tool` | the registered tool name, or `unknown_tool` for an unregistered or disabled name |
| `class` | `read`, `control` or `manage` (absent for `unknown_tool`) |
| `device_id` | the configured device ID, only if the call named a device of the inventory (an unknown ID is client input and is not logged) |
| `ok` | `true` or `false` |
| `application`, `verification` | the outcome axes of the envelope (absent for an internal failure and `unknown_tool`) |
| `error_code` | the domain error code, `UNKNOWN_TOOL` or `INTERNAL_FAILURE` |
| `duration_ms` | integer milliseconds |
| `correlation_id` | the ID of the result |

Never logged: argument values, scene or preset contents, URLs, hosts, headers, request or
response bodies, exception text, file paths or any credential. Every value comes from a fixed
set or from configuration, and a line is at most 512 characters.

- `WLED_MCP_LOG_LEVEL` selects `warning` (default) or `info`. A successful call is an INFO
  line, a failed one (`ok=false`, including `ACCESS_DENIED` and unknown tools) is a WARNING
  line, so the default shows failures only and stays quiet on success. At `info` the startup
  event of [profiles.md](profiles.md#configuration) (transport, profile, number of capped
  devices) is shown too. The level applies to the `wled_mcp` loggers; other libraries stay
  at `warning`, because their INFO lines can contain device URLs.
- `WLED_MCP_LOG_FORMAT` selects `text` (default) or `json` (one JSON object per line with
  `ts`, `level` and the fields above; records that are not call lines carry `logger` and
  `message`).
- An unsupported value stops startup with exit 2 and a message naming the variable and
  never its value. The variables apply to the serving process; the subcommands of
  [cli.md](cli.md) do not use them.
- Text format example (one line):
  `2026-01-01T12:00:00Z WARNING wled_mcp.calls: event=tool_call tool=wled_set_state class=control device_id=desk ok=false application=not_attempted verification=not_requested error_code=ACCESS_DENIED duration_ms=0 correlation_id=0123456789abcdef`

The existing HTTP rejection events (wrong Host, Origin or credential) keep their fixed,
value-free text and now share this format. There is no rate limiting.

## `wled_get_service_status`

Class `read`, no arguments, annotations `readOnlyHint`, `idempotentHint` true and
`openWorldHint` false. It is registered in every profile, second in the tool list. It reads
process memory only: it sends no request to any device, writes no file and starts nothing;
`wled_list_devices` with `probe=true` stays the explicit live check.

`data` (all keys always present):

| Key | Content |
| --- | --- |
| `service` | `name`, `version`, `transport` (`stdio` or `streamable-http`; `unknown` for an embedding that did not say), `uptime_seconds` |
| `access` | `profile` and `devices`: per configured device `device_id`, `max_class` (its cap or `null`) and `effective_class` (the lower of profile and cap) |
| `liveness` | `status: "alive"` and a `definition` text |
| `readiness` | `basis` text, `counts` (`unknown`, `reachable`, `failed`) and `devices`: per configured device `device_id`, `state` and, once observed, `age_seconds`; a failed one also `error_code` |
| `calls` | counters since start: `total`, `ok`, `failed`, `unknown_tool`, `internal_failure`, `by_class` (`read`, `control`, `manage`) and `by_error_code` (only codes that occurred, from the fixed set of the logs) |
| `backups` | `writable_at_startup`: the one advisory check made at startup, `true`/`false`, or `null` when none was made (never reported as writable without a check) |

Semantics:

- **Liveness** is the process answering. It is defined as a TCP connect to the HTTP service
  port or an authenticated MCP `ping`; neither touches a device. There is no unauthenticated
  health route (ISSUE-14-DEC-004, ISSUE-20-DEC-001) and the status tool is not one: it needs
  the same access as every other tool.
- **Readiness** per device is the last outcome of a request this process actually sent to
  that device, recorded by the device client as a side effect of ordinary tool calls.
  `unknown` means no request has been observed since start: it is not healthy and not
  failed. `reachable` means the last request succeeded and `age_seconds` says how long ago;
  `failed` carries the domain code of the last failure (`UNREACHABLE`, `TIMEOUT` or
  `INVALID_RESPONSE`) and its age. A request that never left the process (an exhausted
  deadline, an unusable configured address) is not an observation.
- There is no aggregate "healthy" or "ready" flag: a fleet is summarized only by `counts`,
  and `unknown` is counted as unknown. An old observation says nothing about the device now.
- The counters include calls to disabled tools and failed calls, not the call being answered.
  They reset on restart, hold no per-device or per-argument keys and cannot grow without
  bound.
- `data` contains no URL, host, address, path, credential or configuration text. Device IDs
  are those `wled_list_devices` returns.
- It never reports a stale or unobserved device as healthy and never changes an
  observation: calling it any number of times sends no request.

## Credential rotation and tenancy

- Credential rotation is restart-based. The service reads its bearer credential once at
  startup (`WLED_MCP_HTTP_TOKEN` or `--http-token-file`); to rotate, replace the secret,
  recreate or restart the service and update the client or hub header
  ([DEPLOYMENT.md](../DEPLOYMENT.md)). There is no reload and no second credential. A stdio
  process has no service credential: the MCP host that starts it is its only caller.
- There are no per-credential scopes. One shared credential is one caller class: everyone
  who holds it has the whole reach of the profile (ISSUE-20-DEC-001).
- A shared credential does not give tenant isolation, and neither do profiles or device
  ceilings: a profile is a deployment setting, not a tenancy boundary. Two groups that must
  not share reach need two services (own credential, profile and inventory).

## Liveness and status checks, side by side

| Check | Device contact | Credential | Shows |
| --- | --- | --- | --- |
| TCP connect to the service port | none | none | the process listens |
| authenticated MCP `ping` | none | yes | the process serves MCP |
| `wled_get_service_status` | none | yes | the facts above, including what was last observed per device |
| `wled_list_devices` with `probe=true` | one bounded read per device | yes | the devices' current reachability, explicitly requested |
| `wled-mcp doctor` | read-only probes when asked | as configured | configuration and firmware facts ([cli.md](cli.md)) |

## Compatibility

Additive within the stage-1 contract ([versioning.md](versioning.md#schema-evolution)): a
new tool, one optional output field and no change to any existing tool's input or `data`.
`wled_list_devices` is unchanged. No migration note applies; a client written against
0.1.0 sees an extra optional field and an extra tool.
